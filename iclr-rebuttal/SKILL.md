# ICLR Rebuttal 写作

把评审的每项疑问转化成可核验的回答：**问题定位 → 直接结论 → 证据与条件 → 结论边界 → 修改位置**。优先解决影响判断的科学问题，格式负责降低阅读成本。

需要借鉴真实讨论时，从[按科学问题检索的 13 篇案例库](references/case-library.md)选例。先从当前评语提炼受质疑的结论，再选遇到相同疑问、能说明该用什么证据的案例。领域、年份和评分变化作为标签，便于按需筛选。

## 按需读取

- 起草英文回复、分帖、追问、AC 总结：读 [模板](references/templates.md)。模板是原创示范，按需删减，不是来源原话。
- 写讨论期提醒、询问评分或致谢：读 [审稿人跟进与致谢](references/follow-up.md)，按最后一条评语和现有评分选择话术。
- 统筹完整返修、组织多智能体独立分析与模拟审查、将回复同步到稿件：读 [返修与协作流程](references/revision-workflow.md)。单条润色无需执行完整流程。
- 处理理论正确性、评估偏差、新颖性、统计可靠性或资源效率等通用问题：读 [通用问题手册](references/general-playbook.md)。
- 处理具身论文的记忆有效性、基线公平性、机器人部署等质疑：读 [具身问题手册](references/embodied-playbook.md)。
- 需要引用某位评审的认可或评分变化时，从案例条目进入详录，核对同一人的评语、作者回应和后续反馈。升幅按当届量表数档。
- 判断当年流程、字数限制或解释 ICLR 2026 分数：读 [流程与来源限制](references/process.md)，必要时查目标会议最新规则。

## 输入与证据状态

使用论文及其版本、评审原文/讨论串、已完成实验和修订记录。沿用用户的目标语言和篇幅；未指定时，用中文做内部分析、英文写拟提交回复。

先从用户请求与已有授权明确本轮交付范围：分析、对话草稿、回复文件或论文修改。沿用已授权范围与用户偏好，区分正文和附录限制。修改颜色、页数上限、文件格式、数值舍入规则按当前任务记录，不把某篇论文的约定推广为会议规则。

缺少实验结果时先完成问题拆解与可支持的文字，列出确切缺项。草稿中的缺项写为 `[待提供：数据/实验设置/论文位置]`，不得补造数值、误差条、实验次数或完成状态。若只有评审，没有论文，提供回应框架并标出待核实事实。

为关键证据记录三种状态：

| 状态 | 可用表达 | 不可混淆的情况 |
|---|---|---|
| 已完成且核实 | We evaluated / We have added | 有结果不等于已写入论文 |
| 已有结果、待写入修订稿 | We obtained …; we will incorporate … | 不写 have revised |
| 计划/运行中/缺失 | We plan / This remains untested | 不当作反驳证据 |

同时区分事实来源：原稿记载、原始记录核实、作者明确确认、未确认或相互矛盾。作者确认只适用于其说明的条件和比较对。“相同数据量”不能扩展为相同数据、训练策略或完整预算；未确认也不等于已知不匹配。新确认到来后，更新受影响的主张与表格，删除已失效的疑问，不重复询问已回答的事实。来源冲突时只追问会改变结论的确切缺项。

## 完整返修的工作顺序

按任务规模选用以下环节，不把简单回复扩展成固定流水线：

1. **读当前稿与评审原文**：建立问题覆盖表，识别每项批评背后会改变判断的科学问题。
2. **核对证据与条件**：建立必要的事实记录和比较对，区分文字不清、协议待确认和真实证据缺口。
3. **独立分析并整合**：适合并行时让分析者独立提出回应，随后围绕分歧、原始材料和替代解释协调，主智能体统一事实版本。
4. **起草可独立阅读的回复**：先给结论，再给最小充分证据、必要控制条件与修订位置。
5. **审查核心疑问**：可用独立模拟审稿者检查遗漏和归因错误。将反馈分为文字可修复、作者需确认、必须新增证据或可选扩展，不以一致“通过”为优化目标。
6. **按授权落地并核验**：同步回复与稿件中的术语、数值和条件，检查最终文件、引用与版面，再报告已完成项和仍影响结论的缺口。

多智能体的分工、交接内容和停止条件见 [返修与协作流程](references/revision-workflow.md)。模拟意见只能作为内部检查，不能写成真实 reviewer 认可或录用预测。

## 先建立问题表

覆盖 Weaknesses、Questions 和 Strengths 中暗含的质疑，不只抄 Questions。

| Reviewer / ID | 明确请求及其涉及的科学疑问 | 类型与优先级 | 直接回答 | 证据及状态 | 修订位置 | 讨论状态 |
|---|---|---|---|---|---|---|
| R… / W1、Q2 | 一句话表述 | 核心有效性/比较公平/澄清/边界 | 结论一句 | 证明、表图、协议或运行记录 | 版本+章节/表 | 未回/部分解决/明确认可 |

保留原编号；无编号时自建并说明映射。重复问题可合并为 `W1 & Q2`，复合问题可拆为 `W2-1 / W2-2`。合并后仍逐项检查覆盖，特别区分“请补引用”“请做概念比较”“请新增实验”。不要回答一个相近但不同的问题。

优先处理会改变论文主要结论的问题：证明缺口、假设/量词错误、训练/测试泄漏、错误基线、混杂因素、核心消融、主张超出验证范围。选择能区分争议的最小充分证据：证明、反例、控制实验、统计分析或协议核对，不默认所有问题都要补实验。

### 解读评语背后的顾虑

解读当前评语和使用任一案例时，都先定位评语中的短句，再写清评审明确要求什么、它关系到论文的哪个结论、哪项证据能回答。保留 *if*、*either/or* 等条件。将评审自己写出的判断条件标为**明示**，将根据上下文推断的科学顾虑标为**推测**。同一条评语可以包含多个目的。作者只问“他在意什么”时，直接给出判断和依据即可。

若两种解释会改变回应方式，写出各自的原文依据。例如“能否增加任务”可能关心覆盖面，也可能关心用于选择方法的任务与用于验证的任务是否独立。前者宜补缺失的任务类型，后者宜在未参与选择的任务上检验原结论。用案例对照时，说明哪一点与当前评语相符，并回到本稿核实证据。若只能从旧案例推得某种可能，保留为备选解释。确需追问时，先回答已明确的部分。

收到后续评论时，以评审的新措辞更新判断。“I will reconsider”只支持“愿再考虑”，方向仍未知。若对方点名一项证据解决了一个顾虑，就把认可限定在该项。对作者解释可能的科学顾虑时可列备选，对评审或 AC 发言时只引用可核实的反馈。

## 选择回应方式

| 情况 | 回应动作 |
|---|---|
| 原稿表达不清，已有证据 | 若原稿有歧义，承认并修正；直接澄清，给现有位置与具体变更 |
| 评审指出真实缺口 | 承认，给已完成的证明、实验或协议修正；来不及时限定结论并标明未解决部分 |
| 评审提出替代解释 | 将其改写为可检验假设，匹配控制变量，报告支持与不支持的部分 |
| 指标/模型/协议混淆 | 列明精确版本、输入、训练条件、评估协议，避免猜测评审用了哪个版本 |
| 术语过强或不准确 | 接受准确的替代表述，明确修改，不为标签反复争辩 |
| 新颖性争议 | 如确有共用组件，准确承认；再指出实际新增的机制/数据/理论/分析及支持证据 |
| 部分批评正确，但推论过强 | 接受准确的事实，单独判断它是否影响核心结论；给出依据和仍未解决部分 |
| 请求的实验被其他分析替代 | 解释替代证据回答哪一部分，并明确原请求是否仍未完成 |
| 请求超出本文范围 | 先确认问题价值，说明未验证的具体边界及当前证据能回答什么；不能只说 future work |

不要机械复制案例中的强硬措辞、宽泛 SOTA 声明或未经验证的机理解释。

## 组织回复

### 总体回应（有共同问题或多项修订时）

简短致谢后，概括主要科学补充与对应位置。可用“补充证明”“控制变量实验”“评估协议澄清”“术语及结论收缩”等并列条目。只提真实的 reviewer 认可，不把作者自评写成共识。总体回应不能替代各 reviewer 的独立回答。

### 逐点回应

推荐结构，可根据问题难度缩短：

1. **标题**：`W1 & Q2 — Evaluation protocol and scoring`，用问题主题帮助定位。
2. **直接回答**：第一句表明结论、承认或尚不确定的部分；不要先复述整段方法。
3. **证据**：已存在或新增的证明、实验、控制条件、紧凑结果表或协议说明。先说证据如何对应疑问，再给细节。
4. **边界**：说明现有证据仍不能支持的内容；区分假说、经验观察与形式证明。
5. **修订**：给已核实的章节、表图及版本；尚未落实时用计划时态。

简短事实澄清无需凑齐五段。多个 reviewer 共享结果时保留各自问题的直接答案和最小结果摘要，再交叉引用，避免只写“见另一个回复”。

主回复只保留改变科学判断的细节。复现细节通常放附录，但决定对照是否成立的训练条件应留在证据附近。必要边界用准确的条件和对象自然表达，不为每一项结果追加防御性免责声明。结构允许某种信息流，不等于模型已学会使用该信息，行为主张应对应行为证据。

### 格式与长度

- 使用短标题、少量粗体、短段落；问答表仅在真正利于比较时使用。
- 精简引用评审原文，通常用准确转述；保留关键限定条件，避免复制整段后重复回答。
- 长回复先压缩重复内容；确需因平台限制或可读性分帖时，标题标明 `Response to Reviewer <ID> (1/2)` 并保持编号连续。每帖围绕完整问题群；不要把主张和关键证据拆散。
- 多项定量结果优先在回复中给紧凑表格，让评审就地核查，尤其在用户要求数据表格化时。表格或邻近表注明确指标、单位、方向及必要的样本量和条件，不默认把每个数字做成一张表。
- 汇总表可列均值、SD、已核实的置信区间和必要差值。逐种子完整记录通常留在附录；没有的统计量不补造。不同控制条件的结果分表或明确分组，不能把完整模型的联合收益写成单个因素的增益。
- 成功率绝对差用 percentage points；相对增幅另行计算。平均数、方差、标准差、置信区间不能互换。
- 修订颜色可以辅助定位，不能替代章节/表图索引。核对当前版本编号，不能沿用旧稿页码。
- 不把案例帖数、惯用致谢、颜色或篇幅当作会议硬性规定。

## 追问与结束讨论

追问阶段先识别仍未解决的具体问题，只补增量。若之前理解错了，明确纠正并回答原问题。提醒时先核对最后发言人、评语原意、是否已经跟进及评分字段。未回、没有进一步问题、明确认可、表示将改分、已改分分别记录。对方已表明维持原分或已更新评分时，可感谢具体建议并结束讨论。

需要 AC 总结时，用“主要疑问 → 新证据 → 修订位置 → reviewer 实际反馈 → 剩余限制”。严格区分：reviewer 明示的意见/改分意向、作者转述、AC 推测。未回复不代表认可，愿意 reconsider 不等于已提高分数。不要把录用或分数变化归因于某一句式。

## 交付与检查

按用户任务交付必要部分：问题覆盖表、可复制的回复草稿、待补证据、修订清单。只润色一条时不要强制生成整套材料。生成草稿不包含替用户向 OpenReview 发帖的授权。

检查以下容易出错的实质问题：

- 每个 Weakness/Question 是否回答了本意？引用请求有没有被误作性能比较？
- 每个数字能否追溯到提供的实验？平均值、差值、百分比单位、统计口径是否一致？
- 不确定性对应重跑预训练、后训练还是仅评估？是否误把帧数、rollout 数或相同 seed 编号当成独立训练次数或有效配对？详见 [通用问题手册](references/general-playbook.md)。
- 定义、量词、假设与证明依赖是否一致？理论存在性、最坏情况结论与实际可学习性是否分清？
- 评分聚合、提前停止、缺失值及模型选择协议是否清楚？不同数据、版本、预算的比较是否混为同条件对照？
- 是否把可视化当因果证明，把相关性当干预结论，把小样本当普遍泛化？
- 是否把计划或替代实验写成已完成原请求，把未测试领域/架构写成已验证，或省略收益变小/无明显收益的结果？
- 相同数据与结论在不同 reviewer 回复中是否一致？已修订的位置是否真实存在？
- 若交付 LaTeX 或修改稿，是否编译了当前源文件并检查实际 PDF？页数限制、结论位置、表格溢出及图内旧数值不能仅靠文本搜索确认。
- 是否存在冗长致谢、指责评审、未经用户要求主动索分、指定目标分数、重复催促、或没有证据的“全部问题已解决”？
- 当目标是实际提交时，所有待提供占位都必须被填实或删改成明确的局限；未核实部分单独交给作者处理。
